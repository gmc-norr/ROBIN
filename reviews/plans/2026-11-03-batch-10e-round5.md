## Gate A

1. **Principle:** whether a batch BAM's reads reach target.bam is judged by where the BAM is, not by whether its move reported an error. A finish already judges a BAM that left the claim folder this way.
2. **What would kill it:** any of these.
   - After the fix, a move that took effect and reported an error still reports BAM 1, keeps or lists its claim folder, or makes the SNP check refuse (C15 took_effect, merged_meanwhile).
   - After the fix, a move that did not take effect is let through: BAM 1 not reported, its claim folder dropped, or the SNP check passing (C15 did_not).
   - A BAM in the sample folder whose reads still don't reach target.bam. Then "in the sample folder" would not be enough. Read: finalize merges every `batch_*.bam` there that target.bam's header does not list (`target_analysis.py:3422-3429`), and the step's `to` is such a name.
3. **Refuted before here?**
   - No earlier round ruled on this. Round 4's brief asked it (where Claude was least sure, question 1: "Is there a path where a folder gets `incomplete.txt` and its reads still reach `target.bam` later?"). Codex answered yes, with this case.
   - The finish path has judged by where the BAM is since part 2 (`_install_batch_bam`, the BAM gone from the claim folder: in the sample folder, or merged into target.bam). Only the error path does not.
   - Not a retraction: no earlier result claimed that a move's error means it did not take effect. It was an unchecked assumption in part 2's code.
4. **Simplest thing:** when the move raises, ask the same question the finish asks: is the BAM in the sample folder, or does target.bam list it as merged? If so, the step is done (log a warning). If not, as now: put the index back in the claim folder and report the problem. The question moves into one helper, `_batch_bam_in_place(sample_dir, step)`, used by both paths.
   - Not chosen: checking only that the BAM is in the sample folder. Finalize merges and deletes batch BAMs under its own lock, not the accumulation's (`:3412-3420`). So between the move and its late error, a finalize can merge the BAM and delete it. The finish path checks target.bam for the same reason. C15 merged_meanwhile measures it.
   - Not chosen: checking that the BAM left the claim folder. A BAM gone from both places is lost, and must be reported; the question above already says so.
   - Not chosen: retrying the move. The state after the error already answers it.
5. **Inputs** (read in code at `89550ad`):
   - `_install` runs under the accumulation lock in every caller: the add-up (`:2268`, `:2328`), the finish at the add-up's first locked part (`:2167`), and finalize (`:3394`).
   - Finalize's merge replaces target.bam (`:3290`) before it deletes the batch BAMs (`:3435-3438`). So a batch BAM gone from the sample folder after a merge is listed in target.bam's header.
   - A rename that takes effect removes the old name (rename(2)). One that reports an error may or may not have taken effect (rename(2), BUGS: NFS). No NFS fault is made here: the test makes the real rename, then raises, as Codex did.
   - No other step turns an error into a lasting judgment. The other install steps (replace, remove, append, keep_claim, drop_claim) raise; the list stays, and the next finish does them again, judging by what is on disk. Finalize's merge: an error after its rename ends that finalize with "error" (the SNP check refuses that once); the next finalize finds the names in target.bam's header and does not merge twice (`:3422-3424`).

## Fix

1. **A new helper `_batch_bam_in_place(sample_dir, step)`:** the BAM is at the step's `to` in the sample folder, or target.bam's header lists `to` as merged. The finish path (`_install_batch_bam`, the BAM gone from the claim folder) uses it in place of its own check.
2. **The error path asks it first:** in `_install_batch_bam`, when moving the index or the BAM raises, and `_batch_bam_in_place` is true, the step is done: return None, and log a warning naming the error. Otherwise, as now.
3. The docstring says the BAM is judged by where it is, and why.

## Rulings

- **A move whose index moved and whose BAM did not** (the index's move took effect and reported an error, or the BAM's move failed) is reported as now: the BAM is still in the claim folder, so its reads are not in target.bam. The claim folder keeps both (C15 did_not checks the index is put back).
- **The warning is a log line only**, not a failed file: nothing is missing.
