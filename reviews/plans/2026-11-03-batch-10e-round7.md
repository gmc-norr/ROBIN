# Batch 10e round 7: a ledger that can't be looked up is not "no ledger"

**Locked 2026-11-03, before code.** Base `dddc1fa` (round 6, on the branch, not merged). Branch `fix/batch-10e-recorded-items`. Done by the controller (no agents). No new saved state, so no plan check (the user's rule); Codex reviews the code after.

Codex reviewed round 6's code (`batch10e-r6-code-report-codex.md`, in the run notes folder). The normal path and both plan-check answers are sound. One P2: `clear_bam_failures` asks `os.path.exists(ledger.path)`, and `FileLedger.load()` asks it again. `os.path.exists` returns False on any lookup error (an I/O error, a folder ROBIN may not search), not only when the file is missing. So a ledger that exists but can't be looked up right then is taken as "no ledger": the clear writes nothing, returns 0, and the finish deletes the list. Nothing tries again, and the stale failure stays at every start. Round 6's rule was that a clear that can't be written keeps the list; this is a way around it. Codex measured it by injecting the error at either check; its probe scripts were not run. Claude checked it by reading, and measured `os.path.exists` itself: False with `os.stat` raising EIO, and False for a real file in a folder with no search right, where `open` raises PermissionError.

## Gate A

1. **Principle:** "there is no ledger" is a fact about the file being missing. An error while looking for it is not that fact, and is never taken for it.
2. **What would kill it:** any of these.
   - After the fix, a finish whose ledger lookup fails deletes the list without writing the clear (C19 stat, second_stat).
   - After the fix, a ledger that can't be looked up reads as empty (L8).
   - A ledger that is really missing stops being a quiet skip: no ledger means 0 and no file (round 6's L7, unchanged), and the round-6 and older tests with no ledger still pass (S3).
3. **Refuted before here?**
   - Not a retraction of round 6's design: its rule holds, and this closes a way around it.
   - Round 6's plan made one claim that this round withdraws; see "A correction to round 6" below.
   - The same kind of gap as cases 15 and 16 in the case file: a rule held at the place it was written, with another way in.
4. **Simplest thing:**
   - `FileLedger.load()` opens the file and reads it. `FileNotFoundError`: no ledger yet, an empty state. Any other `OSError`: `LedgerError`, as a read error is now. Its `os.path.exists` check goes.
   - `clear_bam_failures` drops its own `os.path.exists` check. `load()` returns an empty state for a missing ledger, so nothing is written and no file is made, and it raises for a lookup error.
   - `record_bam_failure` keeps its contract (anything it can't do is logged, not raised). Its check becomes "missing" (`FileNotFoundError` from `os.stat`, logged at info, as now), and any other lookup error is logged as an error. Today it is logged at info as "No BAM ledger", which hides a lost failure.
   - **Not chosen:** keeping `os.path.exists` and checking again on error. There is no second answer to ask for.
5. **Inputs** (read in code at `dddc1fa`):
   - The three checks: `FileLedger.load` (`file_ledger.py:185`), `record_bam_failure` (`:497`), `clear_bam_failures` (`:523`). There is no other `os.path.exists` in the module.
   - `load()` already turns an `OSError` from `open` or `read` into `LedgerError` (`:186-191`).
   - The start's intake loads the ledger once, and is meant to stop when it can't be read (`BamIntake.__init__`, `:274`; `workflow_ray.py:3957`, "a ledger that can't be read stops here"). With the fix, a ledger that can't be looked up stops the start too. Today it starts as if there were no ledger, and takes every BAM in again.
   - The finish deletes the list after `_clear_left_out` returns (`target_analysis.py:2103-2107`); its callers catch what it raises and return an error (`:2354`, `:3490`).
   - `os.path.exists` returns False on any `OSError` from `stat` (measured above).

## A correction to round 6

Round 6's plan (`4492af6`), its rulings and its learning (`l-c65e7566`) say finalize does not sync target.bam's contents before deleting the batch BAMs. That was inferred from the Python code alone (there is no `_sync_file` call). Codex measured it with a syscall trace (pysam 0.24.1, samtools 1.24): samtools `fdatasync`s the new target.bam and its index before they are renamed into place, and an injected `fdatasync` error makes the merge raise before target.bam is replaced. So the contents are synced, in this setup. What is left is narrower and not measured: finalize does not sync the sample folder between renaming target.bam into place and deleting the batch BAMs. It is recorded for later as that. Committed records are not edited: the round-6 plan stays as locked, this plan and a new learning say it, and case 18 goes in the case file.
