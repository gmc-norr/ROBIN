**Locked 2026-11-03, after Codex's plan check** (`batch10e-r6-plan-report-codex.md`, in the run notes folder: two P2 findings, answered below). Base `bebf090` (round 5, merged and pushed). Branch `fix/batch-10e-recorded-items`. Done by the controller (no agents).

One P2 remains, older than round 5: a coverage commit's install writes a BAM's failure into the BAM ledger before the list is retired. If retiring fails, or the process stops there, the next finish does the list again, and the batch BAM may then move into place. The BAM's reads reach target.bam, but the ledger keeps the failure, so every start reports "its reads are not in target.bam". It was checked by reading the code and measured with Claude's own test (below); Codex's probe scripts were not run. It does not block SNP calls or lose reads: only the report is wrong.

This round adds a new kind of ledger line and two optional fields: new saved state. So, by the user's rule, Codex checked this plan before any code. The user chose this ("2", 2026-11-03).

## Plan check (Codex) and the answers

1. **[P2] A durable clear can come before the durable move that makes it true.** The draft wrote `cleared` inside `_install`. The sync that puts the batch BAM's move on disk is in `_retire`, after it (`target_analysis.py:2103-2104`, `:3129`). A ledger line is fsynced at once (`file_ledger.py:101`). A power loss could keep the clear and lose the move; a later failure naming the claim would then be ignored. **Accepted.** The finish now puts the install on disk first (`_retire`'s syncs, unchanged), then writes the clears, then deletes the list. C17 checks the order, and the case where the move is lost.
2. **[P2] A clear that can't be written lets the list go.** The draft's clear "logs, does not raise", and `_retire` then deletes the list: nothing would try again. **Accepted.** Skipping (no ledger, or a BAM it has not taken in) returns quietly; anything else that stops the clear (the ledger can't be read, the write or its fsync fails) raises, before the list is deleted. Both callers catch it and return an error, as they do for a failed sync now (`:2351`, `:3463`). The next add-up or finalize finishes the list again. C18 measures it, with the error before the line is written and after.
3. **Implementation note: a clear must not make a step look run.** The intake runs the steps a BAM has no record of (`_resume`, `file_ledger.py:285`). **Accepted:** a `cleared` line never adds a step or a BAM, and a failure it makes the reader ignore adds none either. L6 measures it.
4. **L3 should cover a clear before the BAM's own end line, as well as before a `file_failed` line.** Codex found that order reachable: B's add-up returns, another job finishes the list, then B's job ends. **Accepted:** L3 has both.
5. Codex's answers to the brief's other questions agree with the draft: the claim folder is the right identity; a clear with no failure recorded is fine once the move is on disk; the list of failures is fine (a map by claim would also do); this session's report stays; only claim-tagged failures are cleared; only a finish needs to clear.

## Gate A

1. **Principle:** a failure recorded in the ledger holds only while what it says is true. When a later finish of the same commit puts the batch BAM in place, on disk, the failures that commit recorded for its BAMs no longer hold, whichever line recorded them and in whichever order the lines arrive. A correction that can't be saved must not end the chance to save it.
2. **What would kill it:** any of these.
   - After the fix, a finish that puts the BAM in place still leaves the failure reported at a start (C16 error, killed, own_job).
   - After the fix, a failure that still holds is no longer reported: the finish's move fails too (C16 still_failing); the move was lost before it reached the disk (C17 lost); the BAM has another failure that has nothing to do with this commit (L2, L4).
   - A clear reaches the disk before the move (C17 order).
   - A clear that can't be written, and the list is gone (C18).
   - A clear makes a step look run (L6).
3. **Refuted before here?**
   - Batch 10e part 1, round 2, made another job's failure for a BAM go into the ledger (`file_failed`), so it shows at every start. Only a `start` resets a step. Nothing has ever taken a failure back.
   - Not a retraction: no earlier result claimed a finish undoes a recorded failure.
4. **Simplest thing:**
   - **Tie each failure to its commit.** A failure the install records for a BAM whose reads missed target.bam names the commit's claim folder, as the install list names it (`_staging/_batch_<id>`, unique per commit; `_claim_of`). The `file_failed` line gets `"claim": C`. The failed-file entry gets `"claim": C` too, and when the BAM's own job ends, `record_step_end` copies it onto the end line as `"file_failed_claim": C`.
   - **A finish that puts the BAM in place says so, once that is on disk.** In `_finish_commit`: do the steps (`_install`), put them on disk (`_retire`'s syncs), then, when the batch BAM is in place, write `{"e": "cleared", "key": K, "step": "target", "claim": C}` for each BAM of the batch the ledger has taken in, in one write, then delete the list (`_retire`'s last part). A clear that can't be written raises, and the list stays.
   - **Reading the ledger:** a step keeps its failures as a list of (claim, text), oldest first, and shows the last (`file_failed`, as now). A `cleared` line removes those naming C, and is remembered: a failure naming C that comes after it is ignored. A `cleared` line never adds a step or a BAM. A `start` resets the step and forgets its clears.
   - Written only by a finish: only a finish can follow an attempt that recorded a failure (Codex agrees). Written for every BAM of the batch, whether or not a failure was recorded, because B's own end line can arrive after the finish.
   - **Not chosen: write the ledger failure only after the list is retired.** A stop between retiring and writing loses it. Batch 10e part 1 round 2 closed that gap; this would reopen it.
   - **Not chosen: write the clear inside the install** (the draft). It can reach the disk before the move (finding 1).
   - **Not chosen: write the clear after the list is deleted.** A stop between the two loses the clear for good: no list is left to finish.
   - **Not chosen: clear the step's failure whatever it says.** Clearing by claim takes back only this commit's.
   - **Not chosen: match on the failure's text.** Texts are cut to 500 characters.
   - **Not chosen: one failure slot.** An older failure without a claim, overwritten by C's, would be lost when C's is cleared. L4 measures it.
5. **Inputs** (read in code at `bebf090`):
   - `_install` records the failure for each BAM of a batch whose batch BAM is not in place (`_left_out_of_target_bam`, `target_analysis.py:3057-3073`, called from the batch_bam and keep_claim steps at `:3099` and `:3107`), before `_retire` (`:3122-3138`). `_retire` syncs the appended files, the sample folder (the moved batch BAM, `:3129`) and the claim folder's parent, then deletes the list (`:3135`). A `_retire` that raises leaves the list. A stop leaves it too.
   - `_finish_commit` (`:2081`) does `_install` then `_retire` (`:2103-2104`). Its callers catch what it raises and return an error: the add-up (`:2351`) and finalize (`:3463`).
   - The batch's list names only the BAMs it counted (`bam_refs`, `:2201`, `:2236`).
   - A failure is written twice when a BAM's own target job ran the add-up: the per-BAM handler adds the add-up's failed files to its job (`:2828-2834`), and `record_step_end` writes them on the BAM's end line (`file_ledger.py:409-448`). Measured: C16 own_job checks the end line carries it.
   - The ledger reader keeps one failure per step (`StepState.file_failed`, `file_ledger.py:146`); `_apply` (`:192-213`) raises on an unknown kind. `FileLedger.append` writes all its records in one write and fsyncs (`:215-222`, `:101`); a torn last line is ignored by the reader and cut off by the next write.
   - `record_bam_failure` (`:451-472`) writes only where the ledger has taken the BAM in, and logs, does not raise.
   - The intake runs the steps a BAM has no record of (`_resume`, `:285`).
   - The Coordinator reads only `file`, `error` and `step` of a failed-file entry (`workflow_ray.py:2556-2596`): an extra `claim` field is ignored.

## Fix

1. **`file_ledger.py`:**
   - `record_bam_failure(work_dir, key, step, error, claim=None)`: writes `"claim"` on the `file_failed` line when given.
   - `record_step_end`: a failed-file entry's `claim` goes on the end line as `"file_failed_claim"`.
   - A new `clear_bam_failures(work_dir, keys, step, claim) -> int`: no work folder or no ledger, 0; otherwise reads the ledger and writes one `cleared` line for each key it has taken in, in one write; returns how many. Anything else that goes wrong raises.
   - `StepState` keeps its failures as a list of (claim, text); `file_failed` is the last text, or None. `BamState` keeps the claims cleared, by step. `_apply` handles `cleared` as above, and ignores a failure naming a cleared claim (it adds no step).
   - The module docstring names the new line and fields.
2. **`target_analysis.py`:**
   - `_left_out_of_target_bam` puts the claim folder's name on each entry and on its ledger line.
   - `_retire` is split in two: `_put_on_disk` (its syncs) and `_delete_list` (the rest). `_retire` calls both; the commit path is unchanged.
   - `_finish_commit`: `_install`, `_put_on_disk`, then, when the list's batch_bam step left its BAM in place, `clear_bam_failures` for that step's BAMs, then `_delete_list`.

## Rulings

- **This session's report stays.** The add-up already reported the BAM as a failed file in this session (the GUI and the failed-jobs log); there is no way to take a row back, and none is added. The intake reads the ledger once per session: after a restart the BAM is no longer reported.
- **A `cleared` line for a failure never recorded** is harmless once the move is on disk: it removes nothing, and only a failure naming that claim folder would be ignored. A later attempt of the same list can't make one, because the move it would fail is on disk.
- **The clear rests on what the list's deletion rests on.** The batch BAM is in the sample folder, or target.bam lists it (a finalize merged it meanwhile); `_put_on_disk` syncs the sample folder's names first. target.bam's contents are not synced by finalize, which then deletes the batch BAMs (`:3284-3311`, `:3449-3456`). That is older than this round and puts reads at risk, not only the report. It is recorded for later, not fixed here.
- **A ledger that can't be read or written stops the finish.** The list stays, and each add-up and finalize of that sample returns an error until the ledger works, as for a sync that fails now. At the next start, a ledger that can't be read stops ROBIN anyway.
- **One write for all BAMs of a batch.** A stop part-way leaves a torn last line, which the reader ignores and the next write cuts off. A second `cleared` for the same claim changes nothing.
- **A ledger written before this round** has failures with no claim: they are never cleared, as today.
