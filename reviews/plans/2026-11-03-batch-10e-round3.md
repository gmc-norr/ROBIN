## Gate A

1. **Principle:** a BAM whose reads are not in `target.bam` stops an SNP call, and is reported at every start, whatever stop or error came first. This is the same principle as parts 1 and 2, at three more boundaries.
2. **What would kill it:** any of these.
   - **Finding 1:** a claim folder a finish keeps during finalize, not in finalize's `claims_left`, so the SNP check passes on a `target.bam` that misses reads.
   - **Finding 2:** a batch BAM that could not be written, then a stop after the install list: the finish reports nothing, and the next start shows no failure row.
   - **Finding 3:** a set whose first file moved and whose second move failed: the failure doesn't name the BAM, or no ledger line is written.
3. **Refuted before here?**
   - Part 2's finalize filtered the claim folders it saw before the finish; it never added one the finish kept.
   - Part 2 reported a failed batch BAM write only after the install and the list's deletion, from the worker's memory.
   - Part 1 round 2 read a set's identity from the claim folder only. Its Y6 stopped only the first move.
4. **Simplest thing:**
   - **Finding 1:** `_finish_commit` also returns the claim folders it kept. Finalize adds them to `claims_left`. The SNP check already refuses on `claims_left`.
     - Not chosen: also making the SNP check read `file_failures`. A kept claim folder is listed by every later finalize until someone deals with it; a finish's failed-file entries come once.
     - Not chosen: listing every claim folder after the finish. That could list a new worker's claim taken after the wait.
   - **Finding 2:** when the batch BAM could not be written, the list gets a `keep_claim` step with the problem and the batch's BAMs (with their keys). Doing it reports them as not in `target.bam` (failed files and ledger lines), as a failed `batch_bam` step does. `_claim_of` knows the step, so the kept claim folder and `_staging/` are synced before the list is deleted. The worker no longer reports this failure after the install.
     - Not chosen: recording the failure before the list is written. A commit that then failed before its list would record "its coverage is counted", which would be false.
   - **Finding 3:** read each set's BAM path and key from `_staging/` before any of its files move. A failure uses those.
5. **Inputs** (read in code at `c42f49a`):
   - `finalize_accumulation_for_sample` filters `left`, taken by `_claims_left` before the finish (`target_analysis.py:3370`).
   - `_install` remakes a lost batch BAM's claim folder (`os.makedirs`, `:3076`).
   - `_merge_missed_reads` reads `status`, `batch_bam_error`, `claims_left` and `incomplete_staged`, not `file_failures` (`:3166-3182`).
   - The add-up adds a `batch_bam` step only when the batch BAM was written (`:2290`), and reports a write failure after `_retire` (`:2315`).

## Fixes

1. **`_finish_commit` returns `(entries, kept)`**, where `kept` is the claim folder its list names, when that folder is still there after the finish. Finalize lists the folders it saw before the finish that are still there, plus `kept`. The add-up ignores `kept`: finalize's own list is taken after the add-up.
2. **A `keep_claim` step:** `{"do": "keep_claim", "dir": "_staging/_batch_<id>", "problem": text, "bams": [{"file", "key"}, ...]}`. It is written when the batch BAM could not be written. `_install` reports its BAMs as `batch_bam`'s failure does, and returns the problem. The add-up's own report after the install goes.
3. **Identity before moves:** the claim reads each set's BAM path and key from `_staging/` before moving its files. `failed()` and the list's `bams` use them.

## Rulings

- **A kept claim folder in finalize's list** is right even when the finish only found it: its reads are not in `target.bam`.
- **The failure text for a set moved part-way** still says its files are kept in `_staging/_batch_<id>`; some are left in `_staging/` itself. The set is already not complete, so finalize lists the rest as an incomplete staged set.
