## Gate A

1. **Principle:** a BAM whose coverage the target step could not add is reported at every start, whichever job found it. A set still complete in staging is never reported as lost.
2. **What would kill it:** any of these.
   - A BAM staged by an earlier job, left out by a later accumulation (a target job's, or finalize's), with no failed-file row at the next start, including when the BAM was renamed after staging.
   - A set whose first file move failed, reported "not added", or leaving an empty claim folder that finalize lists.
   - A ledger line written in a work folder that had no ledger, or for a BAM the ledger never took in.
3. **Refuted before here?**
   - Batch 10d's rule: a failed or cut-short step is reported at every start, from the ledger. Part 1 added failures that reach the ledger only when the failing BAM is the job's own (`record_step_end` matches the job's BAMs).
   - Part 1's ruling "a set counts as taken only once its files begin to move" marked it taken before the first move.
4. **Simplest thing:**
   - **Finding 1:** when the accumulation leaves a BAM out, it writes a `file_failed` line for that BAM into the work folder's ledger itself. Then every caller is covered: a target job, a finalize job, an SNP run's merge, the end-of-run finalize and the GUI's own finalize. Not chosen:
     - recording it in `record_step_end`: that sees only jobs run through the workers, not the end-of-run finalize or the GUI's;
     - an `end` line for the other BAM: that would mark the step ended before its own job ends.
   - **Finding 2:** mark a set taken after its first move succeeds. If no set was taken, remove the empty claim folder.
5. **Inputs** (read in code at `01d9edc`):
   - **The ledger:** `FileLedger._apply` raises on a line kind it doesn't know (`file_ledger.py:205-206`).
     - An `end` line sets `file_failed` from its own record, so a later `end` clears an earlier one (`:198-204`). A `start` line resets the step.
     - `_resume` reports a step only when it ended (`:290`).
   - **A BAM's key** is `bam_key(path)`, read from the BAM's bytes (`bam_identity.py`), which assumes a complete BAM is not changed. The intake reads it once the BAM is complete. The staged set keeps only the BAM's path (`source_bam_<n>.txt`, `target_analysis.py:1098`), so after a rename the key can't be read from it.
   - **A set's optional part:** `union_<n>.parquet` is written by staging, moved with the set when present, and read when present (`:2117-2120`, `:2148`); it is not one of the five parts a set needs to be complete (`_STAGED_KINDS`).
   - **The ledger keeps a line for any key** (`_apply` uses `state.setdefault`, `file_ledger.py:191`). A key with no `take` line still becomes a known BAM, and `_resume` then skips each step that has a line.
   - **The intake reads the ledger once, at its start** (`BamIntake.__init__`), so a line written during a session shows at the next start.
   - **The accumulation knows the work folder** (`TargetAnalysis.work_dir`), and the ledger is `<work_dir>/robin_bam_ledger.jsonl`.
     - In finalize, `work_dir` is the sample folder's parent.
     - In the target handler, it is the job's `work_dir`.
     - In the GUI's finalize, it is the monitored folder.
     - These are the folders the intake writes the ledger in.
   - **The move:** `taken.append(n)` comes before the set's first `shutil.move` (`target_analysis.py:2113`).

## Fixes

1. **The ledger gets a line kind:** `{"e": "file_failed", "key": K, "step": S, "error": text}`. Another job found that step S failed for this BAM.
   - `_apply` sets the step's `file_failed` from it, and leaves its other fields alone. An `end` no longer clears an earlier `file_failed`; only a `start` resets the step.
   - `_resume` reports a step that has a `file_failed`, even if it never ended.
   - New `record_bam_failure(work_dir, key, step, error)`. It writes the line only when the work folder already has a ledger, and the ledger has taken that key in. It logs anything it can't do: no ledger, a key it doesn't know, a ledger it can't read, a failed write.
2. **Staging saves the BAM's key** in `bam_key_<n>.txt`, written before the coverage file (which is written last, by rename). It is an optional part, like `union_<n>.parquet`: moved with the set when present.
   - The key is read at staging from the BAM's bytes, while the file is there to be read. It is the intake's key, because a complete BAM is not changed (the key's own assumption).
   - Not chosen: passing the job's key down to staging. It gives the same key, and no test could tell the two apart.
3. **The accumulation calls `record_bam_failure`** for each BAM it leaves out (step `target`), as it makes each failed-file entry, with the key from `bam_key_<n>.txt`.
   - A set staged before this change has no key file: the key is read from the BAM's path, when that still works.
   - When neither works, it is logged, and the failed-file entry is still made.
4. **A set is taken after its first move succeeds.** An accumulation that fails before any set was taken removes its empty claim folder, and reports nothing.

## Rulings

- **No older ROBIN needs to read the new line:** ROBIN is under development, with no older version in use (the user, 2026-11-02). So no step is taken for an older reader.
- **A folder without a ledger gets none** from the accumulation, and **a BAM the ledger never took in gets no line**. A failure line alone would make the next start skip that BAM's target step, which never ran.
- **The key file is optional**, so a set staged before this change is still complete and still counted. Its failure falls back to the path.
- **The job's own BAM** can get two records of one failure: the job's `end` line, and the accumulation's `file_failed` line. Both say the same.
- **The batched path's BAM that couldn't be staged** is the job's own BAM, and is recorded by its `end` line (unchanged).
