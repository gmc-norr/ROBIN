## Gate A

1. **Principle:** a BAM's totals and failures are what ROBIN says they are. Counts that are gone are not treated as counted. A failed file is the failure of the step that reported it. A failure shown to the user is not lost on the way.
2. **What would kill it:** any of these.
   - An update that adds nothing, or counts from zero, while `master_csv_bams.txt` lists BAMs and `master.csv` is missing or holds no counts.
   - A step's own failed file missing from its end record.
   - A sibling step's failed file recorded as this step's.
   - A failed-file row the watcher could not deliver once, then never delivered.
   - A row sent twice that shows twice.
3. **Refuted before here?** Case 15: a record that says "reported" must come after the report. The round-2 code marked an incomplete BAM reported before delivery. And part 2's "a count taken before the handler" assumed an append-only list owned by one job; errors already use an owner tag for this reason (batch 7, `job_outcome`'s `owner`).
4. **Simplest thing:**
   - One check in `update_master_csv`.
   - An owner tag on each failed-file entry when a step writes the list.
   - A queue of rows in the watcher, with the Coordinator ignoring a row it already has.
5. **Inputs** (read in code at `edb85f4`):
   - **`master.csv`:** `_load_existing_data` returns zero counts when `master.csv` is missing. `update_analysis_panel` and `update_sample_overview` then write it from those zero counts, with `last_bam_added` empty. `_read_counted_keys` reads the list on its own. The list is written only after a `master.csv` that holds the key in `last_bam_added`.
   - **Failed files:** every write of the list goes through `context.add_metadata("file_failures", list)`:
     - `bed_conversion.py:559, 640` replace it with the step's own entries;
     - `bam_preprocessor.py:917` copies the old entries and adds one.
     - In the non-Ray runner, sibling jobs share one context and run at once (one per worker thread). `record_step_end` slices the list from a count taken before the handler.
   - **Reports:** `BamIntake.incomplete_too_long` marks a BAM reported before the watcher delivers the row, and a failed delivery is only logged. `_handle` delivers decision rows the same way. `Coordinator.record_cut_short_steps` adds every row it gets.

## Fixes

1. **Finding 1, `master.csv`.** Under the lock, if the list holds keys and either `master.csv` is missing or its `last_bam_added` is empty, the update raises. Nothing is written. The error names both files and says the counts of the listed BAMs are missing. Preprocessing shows it as a failed file (`master_csv`), as for any failed update.
2. **Finding 2, failed files.**
   - `robin.file_ledger.CURRENT_STEP` is a context variable, which each runner's worker sets to the job's owner (`"<job id>:<job type>"`) around the handler call.
   - Both `WorkflowContext.add_metadata` tag each new entry of `file_failures` with that owner; an entry that already has one keeps it.
   - `record_step_end` takes the owner, not a count, and records only that owner's entries.
3. **Finding 3, reports.**
   - The watcher keeps failed-file rows (from its decisions and from incomplete BAMs) in a queue.
   - It sends the queue at once, and again on each tick, until the Coordinator takes it; each row's first failure is logged.
   - `stop()` sends the queue once more, and logs any rows left by name.
   - `Coordinator.record_cut_short_steps` ignores a row whose kind, file and step it already holds this session.

## Rulings

- **An entry of the failed-file list with no owner tag** (written some other way) counts for no step's end record. The Coordinator still shows it, as before.
- **A `master.csv` from before this branch** has no list, so it is still added to (unchanged).
- **The Coordinator's set of rows** is per session: each start shows its rows again, as the round-2 rule says.
