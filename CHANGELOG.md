# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project (almost) adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Security
- **Ray dashboard (SEC-1):** off by default, and on `127.0.0.1` when turned on with `--ray-dashboard` (set `RAY_DASHBOARD_HOST` to bind elsewhere). Its Jobs API runs any command it is sent and has no login; it used to listen on `0.0.0.0`. `--no-ray-dashboard` now really turns it off: Ray's own default started it anyway. `workflow_ray` gains `--ray-dashboard/--no-ray-dashboard` in place of `--no-ray-dashboard`.
- **MGMT R script (SEC-8):** runs `Rscript` with an argument list, not a shell string, so a sample folder name can't run commands.
- **Command templates (SEC-9):** in `--commands` templates and the file watcher's command, `{file}` reaches the shell as data (`$ROBIN_FILE`), so a watched file's name can't run commands in that shell. Templates that start a second interpreter (`sh -c "… {file}"`, `eval`, `ssh host "… {file}"`) still re-parse the name there; use `"$ROBIN_FILE"` inside the inner command instead. Stored command results now show `${ROBIN_FILE}` in place of the path.

### Fixed
- **NiceGUI storage race:** Ray workers get their own empty NiceGUI storage folder, which ends the `FileNotFoundError … storage-general.json.tmp` errors.
- **GUI storage location:** NiceGUI storage (logins, disclaimer state) moves from `./.nicegui` in the start folder to `~/.robin/nicegui`, unless `NICEGUI_STORAGE_PATH` is set. Users see the disclaimer and log in again once after upgrading.
- **Lightweight variant check uses only the sample's own files (VAR-9):** when a sample's `igv/igv_ready.bam` or `targets_exceeding_threshold.bed` was missing, it used the first one found in any sample's folder and saved the result under this sample. It now fails with "… for this sample at <path>", and the results file records the BAM and BED it used. A sample ID that is a path (`../B`) is refused.
- **Every BED interval of a gene is checked (VAR-10):** intervals sharing a name (e.g. one per exon) were reduced to the first. Overlapping intervals are merged, so no position is counted twice.
- **A pathogenic variant counts only when reads support it (VAR-8):** reference-only sites were counted as found. A site now counts with 3 or more alternate reads.
- **The classification panel keeps updating with a classifier disabled (GUI-1):** in a run that enabled only some of Sturgeon, NanoDX, PanNanoDX and Random Forest, the classification panel froze on its first result for the rest of the run while the summary card beside it moved on. The panel now follows the classifiers the run actually enabled.
- **The PDF scores Random Forest against its own cut-offs (REP-1):** the report graded Random Forest on the default 80/50 confidence band instead of its own 85/65, so at 82% the PDF said "High" where the GUI said "Medium" for the same sample.
- **Samples are no longer finalised mid-run after a 60-second pause (JOB-6):** a one-minute gap between BAMs — routine on a live run — marked the sample Complete and merged its `batch_*.bam` files into `target.bam`, so later SNP calls covered only part of the data. The idle timeout now defaults to an hour (see *Changed*). The two consequences are fixed as well: a finalised sample's later reads are merged and reach its SNP calls (see "SNP calls cover every read" below), and unmerged batch BAMs are merged, not deleted, when `target.bam` already exists (with TGT-1).
- **The CNV summary card no longer shows the batch counter as the gain count (GUI-4):** it read `cnv_analysis_counter.txt` as the number of gained regions, so after 37 batches every sample's card said "Gained: 37, Lost: 0". See *Changed* for what the card shows instead.
- **No fake CNV region at the end of every chromosome (CNV-5):** change-point detection treated the end of each chromosome's signal as a breakpoint, adding one spurious region per contig — about 24 per run — to the master BED. See *Changed*.
- **An open page keeps refreshing after a brief reconnect (GUI-2):** a Wi-Fi blip, a laptop waking from sleep or a proxy timeout switched off every refresh timer on the page, which then showed hours-old results with no sign that they were stale. Every page — Summary, Classification, Coverage, MGMT, CNV, Fusion, MNP-Flex, BED coverage and the launcher's own — now keeps its timers until the page is really gone. See *Changed* for the trade-off.
- **A ClinVar update no longer loses pathogenic annotations (VAR-3):** after a new `clinvar.vcf.gz` was downloaded, the index built for the previous file was kept. Region queries then returned no records and exit code 0, so pathogenic variants vanished from the report and the GUI with no error anywhere. The index is rebuilt whenever the file is replaced, and the old index is removed before the rebuild starts — so if indexing fails you get an error and a missing index, never a silently wrong one that the next start-up accepts.
- **`robin add-panel` keeps every region of a gene (VAR-7):** a panel was deduplicated on the gene name alone, so every region after a gene's first — one per exon or tile — was dropped, and coverage, SNP calling and fusion detection ignored them. A panel with 3 EGFR rows and 2 TP53 rows was written out as 2 rows. Exactly repeated rows still collapse.
- **`robin add-panel` reads BED files wider than 6 columns:** a BED12 panel passed validation, printed "added successfully" and was saved garbled (columns 7–10 as chromosome, start, end and gene); a 7- or 8-column BED failed after validation passed. The BED is now read by its first 4 columns, and the rest are ignored. Re-add any custom panel that was added from a BED with more than 6 columns.
- **"Hide Results" in the variant panel opens the file it showed:** after hiding the lightweight variant results, "View Analysis Results" pointed at a fixed path, so it could open a missing file, or one the sample check had turned down. It now re-runs that check.
- **Old CNV breakpoints no longer survive a run that finds none:** after a run with no breakpoints (common since CNV-5), the CNV plot and the master BED kept the previous run's breakpoints. An empty breakpoint file is now written for that run.
- **The newest variant results are the ones shown:** the lightweight variant check writes to one of two places, depending on whether it was started from the sample folder or the monitored root. When both held results, the GUI always showed the nested one, so an old positive could hide a fresh negative. The newer analysis now wins.
- **An opened variant results view stays open:** after a variant analysis finished, its status check kept running every half second and reset the panel each time, so "View Analysis Results" was replaced by the summary almost at once. The check now stops when the run ends.
- **No "None Detected" without usable reads:** an SNV site where no read has a usable base (for example, every read is deleted there) was counted as checked and negative. It now needs review, so the gene reads "insufficient evidence".
- **No "None Detected" on sites no read covers:** a ClinVar site inside a checked region with no reads at all was left out of the results, so a gene whose only such site was unread vanished, and a gene with one negative and one unread site read "None Detected". These sites now need review, each gene's summary counts them (`sites_without_reads`), and the gene details panel shows the count. `sites_checked` counts only sites whose reads were looked at. When the pileup itself can't run (for example, the BAM has no index), its sites read "pileup failed" (`sites_pileup_failed`), not "no reads". A site just before the start of a BED region is no longer checked: it was never part of the region.
- **A failed CNV breakpoint detection keeps the last good breakpoints:** a detection that failed outright, or on every chromosome, used to look like "no breakpoints". It now writes nothing and logs a warning, and per-chromosome failures are logged as warnings too.
- **Fresh variant results no longer say "(legacy location)":** in a watch-folder setup the GUI's own run writes to the location it captioned "legacy", so every new result read as old.
- **The CNV plot's absolute view draws breakpoint lines again:** it read a field the breakpoint array never had, and the error was hidden, so its dashed lines never appeared. Both views now mark the middle of each breakpoint.
- **Results files are never half-written:** the lightweight variant results and the CNV arrays are written to a temporary file and then swapped in, so the GUI can't read half a file and a failed write keeps the last good one.
- **Variant results compare across a clock change:** results now record their UTC offset, so the newest of two results is picked correctly around the autumn clock change.
- **`${file}` in a command template is the shell's own variable:** it used to be mangled into the shell's process ID. Inside single quotes, where the shell expands nothing, `{file}` after a `$` is still the placeholder.
- **`robin add-panel` names the problem when no gene names are given:** a BED whose gene column holds only commas failed with `'chrom'`; it now says "No gene names found in column 4".
- **The per-gene variant check sees its first site:** `analyze_genes` (no callers in ROBIN itself) started its pileup one base late, so a gene's first site was never checked.
- **`{file}` inside `$(...)` stays one word:** in a command template like `"$(dirname "{file}")/out.bai"`, a watched path with a space was split, and the command quietly used a wrong path. The placeholder is now quoted for the context it sits in.
- **The CNV control no longer absorbs patients' reads (CNV-1):** each CNV run handed the cached control (`HG01280_control_new.pkl`) to `cnv_from_bam`, which added the BAM's reads into it. In a long-running worker the control grew with every BAM of every sample, so real gains and losses faded over a run, and a normal sample after an abnormal one showed mirror-image false events. The control's profile is now built from its own counts alone. That also fixes an older wrap: the library sums bins in 16 bits, so early in a run (up to about 24,000 sample reads) the control's profile came out off by several copies.
- **A multi-BAM CNV batch counts each BAM once (CNV-3):** the batch's last BAM was added to the sample's counts a second time, and the saved counts kept it for the rest of the run.
- **A sample's CNV counts keep every batch (CNV-2):** each Ray worker kept its own copy of a sample's CNV read counts and used it without reading the disk, so a batch another worker had added in between was lost for good. Two CNV runs for one sample could also run at once, and the one that saved last overwrote the other's batch. A counts file that couldn't be read was silently reset to none, and the counts were written in place, so a write that failed part-way destroyed them. Each run now reads the counts from disk under a per-sample lock and writes them whole or not at all. Counts that can't be read fail the run and are kept. So does an old-format counts file (`update_cnv_dict.pkl`) that can't be read or moved to the per-sample file: it used to be skipped, and the run then saved over its counts for good.
- **`master.csv` counts each BAM once (JOB-2, first part):** a BAM preprocessed again was counted again. That happened after a restart with the same work folder, when the start-up scan and the watcher both saw it, or for a copy of it in another folder. So BAM passed/failed, bases and mapped/unmapped reads in the GUI summary and the report grew with every rerun. `master.csv` now keeps a list of the BAMs it has counted (in `master_csv_bams.txt` next to it), and a BAM already on that list adds nothing. A BAM is known by its contents (its size and its first and last 64 KiB), not its path. A `master.csv` that can't be read is no longer replaced by a fresh one that counts only the next BAM. A failed update now shows as a failed file instead of only a log line. The other steps that add a BAM's data to a sample's totals (CNV, methylation, MGMT, fusion, target coverage) still add it again when it is run again.
- **A restart no longer runs a BAM's steps again (JOB-2):** ROBIN kept the BAMs it had seen only in memory. A restart with the same work folder sent every BAM through every step again, and the CNV, methylation, MGMT, fusion and target-coverage totals counted it twice. The work folder now keeps a ledger, `robin_bam_ledger.jsonl`: a line when a BAM is taken in, and one when each of its steps starts and ends. After a restart, a BAM's finished steps are skipped and the ones that never started run. A step that was running when ROBIN stopped is not run again, because it may have added its data; it shows as a failed file that "may be incomplete", at every start. A step that failed is not run again either, and shows as failed again at every start; a fail-only BAM's expected failure does not (the non-Ray runner, which has no failed-file list, only logs these). The start-up scan, the watcher and the GUI's "add folder" share one intake, so a BAM they all see, or a copy of it, is taken in once. Watching now starts before the scan, so a BAM that lands meanwhile is not missed. Both runners.
- **A step's batch keeps its own BAMs (found in JOB-2's review):** a BAM's steps share one set of job details, and each batch wrote its list of BAMs into its first BAM's. A step still waiting to run could then work on another step's batch: one BAM's data added twice, and another's left out. Each batch now has its own. Both runners.
- **Ray no longer re-runs a per-BAM step whose worker died (found in JOB-2's review):** Ray runs a task again, up to 3 times, when its worker dies, for example when it is killed for running out of memory. A step that had already added the BAM's data then added it again. The six per-BAM steps now fail instead, and show as failed.
- **The watcher sends every BAM it takes in, or says which it couldn't (JOB-4):** the Ray watcher held new BAMs' jobs and sent them only when the next file arrived, so the last BAMs of a run could wait for good. A failed send dropped the jobs without a word. And at shutdown the Coordinator was told to stop first, so it ignored what the watcher sent after. A timer now sends waiting jobs every half second. A failed send is logged with the BAMs' names and tried again. At shutdown, ROBIN stops watching and sends what waits before the Coordinator stops; anything still unsent is logged by name, and the BAM ledger runs it at the next start.
- **A half-written BAM is checked again, and one that never completes is shown (JOB-4):** a BAM found half-written by the start-up scan, or whose writer stopped, was never looked at again without a new file event. The timer now checks it again: it is taken in once it completes. One that stays incomplete and unchanged for 10 minutes shows once as a failed file ("not analysed"); it is still analysed if it completes later. A failed-file row the Coordinator didn't get is kept and sent again, and the Coordinator shows a row it already has only once. Ray runner only.
- **A BAM still being written is not read (JOB-4, in part):** a BAM copied in with `cp` or `scp` was read as soon as it appeared, half-written. A BAM is now taken in only once it ends with the BAM end-of-file block.
- **The target step shows a BAM whose coverage it could not add (noted by batch 8):** a BAM whose staged coverage couldn't be read was left out of the coverage totals while the step said "success", and so was a BAM that couldn't be staged in a batch. When a BAM came in alone, a failed add-up (a lock wait that ran out, an error) wasn't reported at all; nor was a batch BAM that couldn't be written, whose reads then missed `target.bam`. Each such BAM now shows as a failed file that says what happened and which `_staging/_batch_<id>/` folder keeps its files. Finalize shows the ones its own add-up couldn't add. It is also kept in the BAM ledger, so it shows again at every start, whichever job found it, and even if the BAM was renamed since (staging keeps its key) or a move took only some of its staged files. A lock wait, or a file move, that fails before any of a BAM's files is taken is not a failure: the files stay staged for the next add-up.
- **The variant check names the regions it could not check (noted by batch 9):** an error in one region dropped that region: its genes vanished from the results, the job reported success, and the GUI said "completed successfully!". The results file now lists such regions (`regions_failed`, with their genes and intervals), the job counts as failed, and the GUI names them, in red after the GUI's own run. The other genes' results are kept. A BED line that isn't a BED row now stops the check, naming the line, instead of reading as no regions at all.
- **A batch's coverage reaches every file, or none (TGT-3):** adding a batch wrote about ten coverage files one after another, then moved its batch BAM to where finalize looks. An error or a crash part-way left some files with the batch and some without, for good, and its claim folder stranded. Now every file is prepared in `<sample>/_commit/`, with a list of the steps that put them in place (`install.json`). Once the list is written the batch counts; a stop part-way is finished by the next add-up or finalize, even after a second stop. The time series is cut back and appended again, so a half-written append is put right. A list that can't be read stops that sample's add-ups with an error naming it. A batch BAM that couldn't be written, or that is missing from both its claim folder and `target.bam`, shows its BAMs as failed files, also after a stop part-way, and no SNP calls are made on a `target.bam` without its reads, whichever job found them. A batch BAM whose move reported an error but took effect, as a rename over NFS can, is not reported missing. Files are synced to disk in an order meant to hold after a power loss; a crash of the process is tested, a power loss is not.
- **The watcher's BAMs get the reference genome (JOB-8):** BAMs found at start-up got the reference and BAMs that arrived later didn't, so MGMT, target, CNV and fusion ran differently depending on when a BAM appeared. Both now get the same settings.
- **Methylation numbers now match ONT's modkit (METH-1 to METH-6, METH-13, METH-14):** the per-sample methylation table feeds every classifier, and was wrong in several ways at once. Tested against `modkit pileup --cpg --combine-mods --combine-strands --filter-threshold 0.73` on synthetic reads: every CpG now matches it exactly, however the reads are split into batches.
  - **Batches are summed, not averaged (METH-1, METH-2):** each batch's percent was averaged with the running percent, so the newest batch always weighed at least half (50 reads at 80% and then 1 read at 0% stored 40.0%; the truth is 78.4%). The first batch wasn't aggregated at all, so random forest could see over 100%.
  - **Both strands of a CpG count together (METH-4):** NanoDX and PanNanoDX only ever saw the plus-strand reads, about half; Sturgeon counted the two strands as two equal votes; random forest and MNP-Flex got two rows per CpG.
  - **Unsure calls are left out of coverage (METH-3):** 6 methylated, 2 unmethylated and 2 unsure calls read 60% instead of 75%. This also changes MGMT's input.
  - **Implicit-mode MM tags are read (METH-13):** in BAMs whose MM tags use `.` or no marker, unmarked Cs mean "unmethylated", and they were ignored, pushing methylation up. BAMs in `?` mode are unaffected. Only CpG Cs count, and ROBIN reads "CpG" from the read, since it has no genome file at this step: where a read has a typo at a CpG's G, modkit still counts the C and ROBIN doesn't, as in `?` mode. A read with an MM tag but no ML tag (no probabilities) is skipped, as modkit does.
  - **A low-quality read is dropped whatever its record order (METH-14),** and only primary alignments count, as in modkit.
  - **The CpG panel is read as it is written (METH-6, METH-5):** `parquet_filter.txt` is 0-based already (checked against hg38); v0.5's "1-based" shift widened every CpG to take in the base before it. Duplicate panel rows no longer double the counts, and the panel cache in a sample folder can no longer go stale.
- **Target coverage numbers match samtools (TGT-1 to TGT-5):** tested against samtools run once on all of a sample's reads, with the reads split into 1, 2 and 4 BAMs, in different orders, and with two workers at once.
  - **"Global coverage" is mean depth (TGT-3):** it was the covered bases of each BAM summed, divided by the genome length, and shown with an "x". Covered bases per chromosome are now exact.
  - **Two workers no longer overwrite each other's coverage (TGT-4):** the totals are read, added to and written in one locked step.
  - **Every BAM's panel reads reach target.bam (TGT-1):** BAMs that arrived before any target passed the call threshold never reached the SNP input, and a second finalize deleted every batch BAM made since the first without merging it. A batch's reads now reach `target.bam` only once its coverage is counted, and a finalize no longer holds up the coverage step while it merges. IGV's copy, `igv/igv_ready.bam` (the per-gene variant check reads it too), is rebuilt when `target.bam` gains reads; it stopped at the first finalize.
  - **The panel always reaches target.bam (TGT-2):** with fusion off, the CNV step's master BED held breakpoints but no panel, and target extraction used it alone.
  - **The panel's depth counts each base once (batch 8):** "Targets Estimated Coverage", and the enrichment ratio and quality label made from it, added up the panel's rows, so where rows overlap the reads there counted twice. In the AML panel that is 3.6% of its length. The number is now samtools over the panel with overlapping rows merged. rCNS2 has no overlaps, so it doesn't change. Each target's own depth and "% of targets above" are unchanged.
  - **Split reads count once (TGT-5):** supplementary alignments were counted as extra reads in read counts, yield and the 50,000-read gate.
- **Failures are visible (ERR-1, METH-8, VAR-4, REP-6):** a step that failed or never ran now says so; "none found" appears only when the step ran and found nothing. Each fault below was injected on purpose and checked where a user looks: the failed count, `failed_jobs.csv`, the GUI's errors and the PDF.
  - **A failed job counts as failed (ERR-1):** MGMT, CNV, target, fusion, Sturgeon, NanoDX, PanNanoDX and random forest filed their errors under a name the scheduler never checked, so their failures counted as completed and were missing from the failed count and `failed_jobs.csv`. The `high` preset and the non-Ray runner (`--no-use-ray`) counted only crashes. Now any error a job files while it runs fails that job, whatever its name; an error left by an earlier job doesn't. The expected failures of fail-only BAM submissions stay expected.
  - **Errors reach the GUI (ERR-1):** the workflow monitor's error counts were never sent, and its "Recent errors" box always said "No errors detected." Both now show failures: job type, sample and message. Warnings raised inside workers ("BAM Alignment Warning", "Skipped (too many reads)") used to be dropped; they now appear when their job returns. A job that crashes sends its warnings with that worker's next job, or not at all. Error counts and forwarded warnings go out at a priority the GUI neither drops when it is busy nor merges with the update before. When more events arrive between two refreshes than the workflow keeps (200), the GUI says how many earlier messages were not shown, and refreshes its error counts anyway. If the failures' details are gone by then, the summary says "N failures recorded; the details are no longer available." instead of "No errors detected.".
  - **A BAM that fails in methylation conversion is reported (ERR-1):** one failing file in a batch was logged, its data deleted, and the job reported success. Each failed file now gets a `failed_jobs.csv` row and a line in the GUI's errors; the batch's other files still go on to the classifiers.
  - **Classifier failures are no longer reported as success (METH-8):** Sturgeon swallowed its errors; NanoDX and PanNanoDX saved a row with no scores, and wrote the sample's methylation calls to `errordf.csv` in the worker's current folder; an MGMT R failure returned success. Each is now a failed job. NanoDX saves no row and writes no `errordf.csv`. MGMT still keeps its BED file.
  - **A failing step runs once (JOB-3):** with Ray, a step that raised was run a second time without its work folder, reference or panel, which doubled its side effects and could write output next to the BAM. It now runs once. The bare call is used only for a step that can't take those arguments.
  - **"No pathogenic variants" only when ClinVar ran (VAR-4):** when the ClinVar database was missing or SnpSift failed, the plain snpEff file was copied in as `snpsift_output.vcf`, and the report read it as "annotated, none found". The ClinVar step now writes `##ROBIN_ClinVar=annotated` or `##ROBIN_ClinVar=unavailable;reason=…` into the file. The report then says, for example, "ClinVar annotation was unavailable for the SNP file (ClinVar database not found); pathogenic SNP variants could not be assessed.", and the SNP card shows "ClinVar: unavailable (…)". The file is written to a temporary name and swapped in, so it is never empty while SnpSift runs.
  - **The fusion report tells "not run", "unreadable" and "none found" apart (REP-6):** all three printed "No fusion candidates were identified." They now read "Fusion analysis has not been run for this sample.", "The fusion results could not be read." and "No fusion candidates were identified.". A failed fusion build fails the job, and is rebuilt on a later run. The target panel and the genome-wide results are judged apart: if one can't be read, the report says so even when the other has candidates. While a build's last attempt has failed, an earlier run's candidates are shown with "The latest target-panel fusion build failed; these results are from an earlier run." (or genome-wide). If those candidates hold no validated fusion, the summary and the body say the latest build failed and an earlier run found none. The GUI's fusion panel says, for each type, "has not been run yet", "could not be read" or "No fusion candidates were identified", where it said "No fusion data available" whatever the reason. The methods text stated the wrong filters (mapping quality > 50, > 200 bp, 4 or more reads): it now gives the ones the code applies, taken from its settings: mapping quality of at least 50, mapping span of at least 250 bp, at least 3 reads per gene pair, and 4 or more reads at the same validated breakpoint for a fusion to be reported.
- **Pathogenic means what ClinVar says (VAR-1, VAR-2):** checked against ClinVar's own GRCh38 file (2026-10-25, 4.6 million records).
  - **"Conflicting" no longer counts as pathogenic (VAR-2):** the variant check, the GUI's SNP table and the report counted any ClinVar label containing "pathogenic", including "Conflicting classifications of pathogenicity". That was 182,153 records, a third of all ROBIN flagged; one is a TP53 record whose submitters say "uncertain" and "likely benign". A record now counts when ClinVar's own label says so: pathogenic or likely pathogenic (germline), oncogenic or likely oncogenic, or somatic Tier I or II. "Conflicting" alone doesn't count, and there is no vote over the submissions.
  - **BRAF V600E and TERT C228T still count:** their germline label is "conflicting", and they had counted only by that accident. They now count by their oncogenic and Tier I labels. 701 records that carry only such labels now count too, for example an H3-3A Tier I site.
  - **The labels are shown:** the GUI's SNP table shows ClinVar's oncogenicity (ONC) and somatic impact (SCI) next to CLNSIG. The variant check's significance reads, for example, "Conflicting_classifications_of_pathogenicity; oncogenicity: Oncogenic; somatic impact: Tier_I_-_Strong". The report's note states the rule. The report's unused vote over conflicting submissions is gone; it would have crashed if reached.
  - **Every ClinVar record at a position is checked (VAR-1):** the variant check kept one ClinVar record per position, the last in the file, so 67,276 were never checked. At IDH1 R132 it kept R132S, so a sample with R132C read "insufficient evidence". At KRAS G12 it kept a two-base change it can't call, so G12D was never checked. Each record is now checked on its own allele.
  - **SNP rows without a gene annotation are shown (VAR-2):** a variant with no snpEff annotation vanished from the SNP table when other rows had one.
  - **A ClinVar record with no alternate allele no longer wipes out its gene:** 13 pathogenic ClinVar records give no alternate allele (ALT ".", the reference base itself). The variant check failed on them and dropped the whole gene from its results, with only a log line. Before this release that hit PTEN (AML panel) and BRCA2 (both panels); keeping every record at a position added BRCA1. These records are now skipped and counted (`clinvar_records_not_checkable` in the results), with one warning in the log.
  - **The variant check's HTML export counts found variants only:** it counted every checked ClinVar site that had reads as a found pathogenic variant. Nothing in ROBIN calls it. It now gives the same status and counts as the JSON results.
- **No request for a classifier or SNP run is thrown away (JOB-1, JOB-5):** checked through a real Coordinator, with requests sent while a run was busy.
  - **Every sample gets a classification after its new data (JOB-1):** each classifier type (Sturgeon, NanoDX, PanNanoDX, random forest) runs one job at a time across all samples, and kept one waiting job for all of them. A third sample's request found that slot taken and was dropped, as was new data for a sample while another waited. So in a run with several samples, a sample's last classification could be older than its data, or never happen. Each sample now keeps one waiting job per classifier type. Waiting samples take turns, oldest first, and the run starts after the sample's newest data.
  - **A second SNP request runs (JOB-5):** after a sample's first SNP analysis, every later request for it was skipped for the rest of the session, while the GUI said "queued". Now one runs and one waits per sample. More requests while one runs merge into the one waiting run, which carries the newest request's settings (such as forced regeneration). SNP requests are no longer batched: a batch ran with its first request's settings.
  - **A waiting request never waits for room:** when a run ended, the request waiting for it was started as new work, which waits while the scheduler's backlog is full. That wait happened inside the ended job's own finish step, and its pool slot stays busy until that step returns, so with a full backlog nothing could move again. Work already accepted now joins a waiting list at once. Found by an external review.
- **SNP calls cover every read, and a finalize runs once (JOB-6, JOB-7):**
  - **A finalised sample still gets its later reads (JOB-6):** once a sample was finalised, the GUI skipped the merge for it for the rest of the session. New batch BAMs never reached `target.bam`, and an SNP run used the old one. Files still staged also counted as "nothing to merge". Each finalize now checks the disk, and every Live → Complete starts one.
  - **An SNP run first merges new reads:** from every SNP button, the SNP job merges new batch BAMs and staged files into `target.bam` before it calls variants. It waits for a worker still adding reads. If any read could not be added (a lock timeout, unreadable staged files, a staged file missing a part, a batch BAM that could not be written, or a worker that stopped), the SNP job fails and says why.
  - **Earlier SNP calls are reused only when they came from the same reads:** all three SNP buttons reused a sample's existing calls whenever they existed, so new reads never reached the calls unless regeneration was forced. A finished call now records which `target.bam` it read (its batch BAMs, size and time). Earlier calls are reused only when that matches and nothing waits to be merged.
  - **Staged reads that could not be added are kept:** when a batch BAM could not be written, or a staged file could not be read, its staged files were deleted, and those reads never reached `target.bam`. They are now kept in their `_staging/_batch_<id>/` folder, with an `incomplete.txt` that says why. Found by an external review.
  - **A part-failed SNP call fails:** a Clair3 region that failed was skipped, and VCFs left from an earlier run were used when this run wrote none. So calls missing a region, or old calls, were shown as complete. Each run now writes Clair3's files into its own new folder (`clair3/run_<id>/`), and each region must finish and write both VCFs there. A failed VCF merge fails the run too. Found by an external review.
  - **A finalize runs once (JOB-7):** when the finalize job was queued, the GUI also ran the same merge itself. Two merges at once could delete each other's batch BAMs; batch 6's lock already stopped that (measured), so this was wasted work. The GUI now merges itself only when the job can't be queued.

### Changed
- **Coverage results for the same data change:** "Global coverage" is now mean depth, so it and the enrichment ratio change. Target depths shift a little: a target's length is end − start (it was one more), and deletions no longer count as aligned bases, as in `samtools coverage`. `coverage_main.csv` gains a `bases` column, and a sample folder gains `_covered_stretches.parquet`. In a folder written before this change, depth carries on, but covered bases can't be recovered: they are left blank in `coverage_main.csv` (no screen shows them). That folder's coverage-over-time chart changes meaning at the same point: covered bases over genome length before, mean depth after. Mapped reads, bases and yield drop for split reads. `target.bam` holds the records overlapping the panel (and the master BED's regions), as `samtools view -L` gives them: no longer the off-panel pieces of panel reads, and now the in-panel pieces of reads whose primary is elsewhere.
- **Methylation results for the same data change:** every classifier's input changes, so Sturgeon, NanoDX, PanNanoDX, random forest, MNP-Flex and MGMT results can change. The per-sample `<sample>.parquet` now holds one row per CpG (strand `.`, at the C), with `valid_cov = n_mod + n_canonical` and percent from those counts; its `_metadata.json` says `"column_format": "cpg_counts_v2"`. A sample's existing parquet is converted on its next merge: its summed counts are kept, its minus-strand rows move onto the C, and unsure calls leave its coverage (coverage is recomputed from the counts). What the conversion can't undo: implicit-mode Cs it missed stay missed, and low-quality reads and supplementary alignments it counted stay counted. For exact numbers on an old run, delete the parquet and run bed_conversion again. Supplementary alignments no longer count toward methylation.
- **A sample's CNV runs take turns (CNV-2):** a second CNV run for a sample waits for the first, up to 3 hours, then fails. A sample whose counts file, or old-format `update_cnv_dict.pkl`, can't be read now shows a CNV failure on every run until someone deals with the file; it used to start again from no reads.
- **`master.csv` gains a column and a list file (JOB-2):** `last_bam_added`, the key of the last BAM it counted, and `master_csv_bams.txt` next to it, the keys of all of them (one per line). The list is a file of its own because one CSV cell can't hold thousands of keys. A `master.csv` written before this change has no list, so the BAMs it already counts can be counted once more after a restart. For exact numbers, use a new work folder. A `master.csv` that can't be read now shows a failed file for each BAM preprocessed until someone deals with the file; the GUI's overview and the panel update leave it as it is (they used to reset it). So does a `master.csv` that is missing, or was written again without its counts, while the list still names BAMs: their counts are lost, and counting from zero would hide that.
- **The work folder gains `robin_bam_ledger.jsonl` (JOB-2):** one JSON line per BAM taken in, and per step start and end.
  - A work folder from before this change has no ledger, so at the next start its BAMs are taken in as new and their steps run again (only `master.csv` won't count them twice). For exact numbers, use a new work folder.
  - A ledger that can't be read stops the Ray runner's start with a message. The non-Ray runner logs it for each BAM and analyses none. Moving it away starts the folder's record again, and BAMs done before may then be counted again.
  - A step cut short by a stop, or one that failed, shows as a failed file at every start, and is not run again (the non-Ray runner only logs it).
  - A BAM that never completes (no end-of-file block) is never analysed. After 10 minutes unchanged, the Ray runner shows it as a failed file; the non-Ray runner only logs it.
  - Per-sample steps (classifiers, IGV BAM, SNP, finalize) are not in the ledger.
- **CNV results for the same data change (CNV-1):** `CNV2.npy` is now the control alone, so `CNV3.npy`, the sex estimate and the chromosome statistics change with it, most early in a run and later in a long run. A contig that only the sample's BAM has (not in the control) is left out of `CNV3.npy`; it used to be compared with its own reads. CNV runs are also faster: each BAM is read once, not a second time for the control's profile.
- **Lightweight variant results:**
  - New gene status "Insufficient Evidence": a site with 1–2 alternate reads, an indel or multi-base change (which a pileup can't call), or reads showing neither allele.
  - Each checked site has `supported` and `needs_review`. The per-gene counts and the totals count supported sites only.
  - New keys: `sites_checked` and `insufficient_evidence_sites` per gene; `total_sites_checked`, `genes_with_good_coverage`, `input_bam`, `input_bed` and `sample_id` in the metadata.
  - The GUI's variant tables list sites that are found or need review, with their evidence level.
  - **Old results files are not shown:** they don't record which BAM they used. Run the variant analysis again.
- **Sample-completion timeout is an hour, and configurable (JOB-6):** the idle time before a quiet sample is marked Complete and finalised is now **3600 s**, not 60 s. Set `ROBIN_COMPLETION_TIMEOUT_SECONDS` to a number of seconds to override it; unset, empty, non-integer and values below 1 all mean 3600 (a `0` that was honoured would finalise every sample on the first tick and delete its unmerged batch BAMs). **If your deployment relied on samples finalising a minute after the last BAM, it now waits an hour** — set the variable to get the old timing back.
- **The CNV card's gained/lost counts read "Not available" (GUI-4):** the card shows "Gained: Not available", "Lost: Not available" and "Gained vs total: —" unless a `cnv_results.csv` supplies real counts, and nothing in ROBIN writes a per-sample gain/loss count today. It used to show a number for every sample. If you read "Gained: 0" as "no gains were found", that reading is gone: the card now says it does not know.
- **Fewer CNV breakpoints per run (CNV-5):** `breakpoints_count` in a sample's `cnv_detector_state/tracker_metadata.pkl` drops by about 24 per run, one per contig analysed. When every chromosome yields only a series terminator, `cnv_data_array.npy` and `breakpoints_NNN.bed` are not written at all; every reader of those files already handles their absence.
- **A closed page is torn down up to 60 seconds later (GUI-2):** a page's refresh timers and theme listeners are released when the browser client is discarded rather than when the socket drops, so for a page that really was closed this happens after ROBIN's `reconnect_timeout` of 60 s instead of immediately. That is the cost of surviving a reconnect.
- **A classifier the report can't identify is dropped rather than mis-scored (REP-1):** when the report cannot match a classifier's display name to its confidence-threshold config key it now raises, where it used to fall back silently to the default 80/50 band. The report still finishes: the existing per-classifier handler logs `Error processing <name> classification: Unknown classifier …` and leaves that classifier's row out of the PDF's summary table. Nothing triggers this today — the report's four display names are a literal list matching the four known classifiers, and a test pins them to the GUI's — so it bites only if those lists ever drift, and then it costs a missing row and a log line instead of a wrong confidence band.
- **More failures show up (ERR-1, METH-8):** runs that looked clean can now show failed jobs: those failures were always there. A job that files an error no longer starts the jobs after it. On the `standard` preset only `target` has one, `igv_bam`; finalize still refreshes IGV's copy. On `high` and `--no-use-ray`, where a filed error failed nothing before, a failed `bed_conversion` now also stops the classifiers, and a failed `preprocessing` the jobs after it. MGMT counts as failed whenever its R prediction doesn't run (no `Rscript`, no script, or an R error), so **a setup without R shows an MGMT failure on every run**. A BAM with no reads that reaches CNV is a failed CNV job, also in a fail-only submission. `failed_jobs.csv` gains rows of kind `file_failed`, one per failed file in a job that otherwise went on. `--no-use-ray` mode now marks fail-only submissions by the same two rules as Ray, so a fail-only BAM's expected classifier failures count as expected there too.
- **ClinVar status in the variant files (VAR-4):** `snpsift_output.vcf` and `snpsift_indel_output.vcf` carry a `##ROBIN_ClinVar=` line after `##fileformat=`. For a file written before this change, the report and the SNP card say the ClinVar status was not recorded, not "none found". A sample whose annotation was recorded unavailable is not annotated again by itself once ClinVar is available: run its SNP analysis again with regeneration forced.
- **Fusion files (REP-6):** when no read passes the filters, the fusion step writes empty `fusion_candidates_*_processed.pkl` files, so an earlier run's candidates can't show as the latest. A folder from before this change is read from its `sv_count.txt` and candidate CSVs. A build that fails writes `fusion_candidates_*_processed.pkl.failed` next to its pickle. The next build rebuilds the pickle from the candidate CSV, even if it brings no new reads, and removes the file if the rebuild works. If the CSV is missing or empty, the build fails again and the file stays. A fusion job that fails before it builds (a staged file that can't be read, say) writes it for both types. **A fusion candidate file that can't be read now fails the fusion job** and names the file. Before, it was logged and skipped, and a staged file was then deleted: its reads were lost, and the target panel could say "No fusion networks identified". Staged files stay until they can be read. Staged files and accumulated parts are written under a temporary name (`*.parquet.tmp`) and renamed into place.
- **Panel depth file (batch 8):** a sample folder gains `target_union_coverage.csv`, the aligned bases over the merged panel, and the staging folder a `union_*.parquet` per BAM. In a folder written before this change, or a sample with a BAM staged before it, the panel depth stays the old row sum. It also falls back to the row sum, for good, if the file stops matching the row totals beside it: after a commit that failed part-way, a panel changed mid-run, or a staged part that can't be read. A partial merged total is never shown.
- **Pathogenic flags change (VAR-1, VAR-2):**
  - Fewer variants are flagged pathogenic in the SNP table, the report and the variant check, and a few somatic ones are added.
  - The report follows the new rule at once. Saved SNP tables (`clair3/snpsift_output_display.json`) and saved variant-check results keep their old flags until the sample's SNP step, or the variant check, runs again.
  - The variant check lists every ClinVar record at a position. A found variant's neighbours there read "no support". When every read carries the found allele, they read "reference mismatch" (needs review). The gene's status follows the found variant.
- **More classifier runs with several samples (JOB-1):** each sample with new data now gets its own classifier run, where one waiting run was shared by all samples. Each classifier type still runs one job at a time, so classifiers do more work, and a sample may wait for other samples' runs first.
- **SNP calls are made again once (JOB-6):** existing SNP calls don't record which reads they came from, so a sample's next SNP run calls variants again, once, even without forced regeneration. A call now writes `clair3/target_bam_source.json`. A sample that gained reads since its last call gets new calls on its next SNP run, and bulk SNP now includes it. An SNP run with reads waiting to be merged takes longer: it merges them first, and waits up to 5 minutes for a worker still adding reads. Clair3's raw files now go in a new `clair3/run_<id>/` folder for each run; earlier run folders are deleted when possible (the container writes as root, so some may stay).
- **More SNP runs say "failed" (JOB-6):** SNP calling now fails when one Clair3 region fails, where it used to leave that region out. A sample with a kept `_staging/_batch_<id>/` folder (staged reads that could not be added) gets "failed" from every SNP run until someone deals with the folder.
- **Pins:** `robin.yml` pins `numpy=1.26.4`, `pandas=2.1.4` and `scikit-learn=1.8.0`; `pyproject.toml` pins `scikit-learn==1.8.0` (the version the NN model pickles were saved with) and requires Python `>=3.12,<3.13`.
